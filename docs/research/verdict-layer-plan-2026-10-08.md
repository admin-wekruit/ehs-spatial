# 判定层计划：严格、解耦、可比较多种方案（2026-10-08）

目标（用户）：重建之后的判定层要更严格、更解耦，而且要像研究机构一样，能把多种解决方案放在同一基准上比较结果。
这份计划只做计划，不开工。架构见 `verdict-layer-architecture-2026-10-08.md`（七层四契约），评测见 `verdict-evaluation-protocol-2026-10-08.md`，
路线见 `verdict-spec-to-check-2026-10-08.md`。原则沿用 10 月初换模块的做法：**同一条流水线，一次只换一个模块，先证明等价，再归因差异**。

## 0. 三个目标各自的抓手

| 目标 | 抓手 | 验收 |
|---|---|---|
| 严格 | 每条判定可复现：版本三元组（场景 schema / 规则包 / 引擎）+ 输入哈希 + 固定输出 schema；判定只由确定性引擎出；值 ± U + 护带 + 五态；每条判定带证据链和"什么能推翻我" | 同一输入同一版本两次运行逐字节相同；任何判定翻转 CI 失败 |
| 解耦 | 四个契约（C1 场景、C2 事实、C3 签名、C4 规则包）用 pydantic + JSON schema 固化；每层一个 `Protocol`；跨层 import 由 lint 禁止 | 换任一层的实现，其它层的测试不改一行 |
| 可比较 | **变体注册表 + 实验台账 + 记分卡**：每层可注册多个实现，一次 run = 冻结基准 × 每层一个变体；同一张表比所有变体 | 任何两个变体的差异能归因到单一层；记分卡自动生成 |

## 1. 实验台（lab）怎么设计

```
registry.yaml            每层的变体：L1.photo-v2 | L1.daaam ; L2.relations-v1 ; L3.none | L3.stpl-v1 ; L4.template(baseline) | L4.clause-kg ;
                         L5.funclib | L5.codegen | L5.redundant ; L6.clingo | L6.prolog | L6.python ; decision.guard_k2 | decision.simple
benchmark/<snapshot>/    冻结的 (工位, 照片 / 场景契约, 规范包, 金标)；哈希清单
runs/<run_id>/           config.yaml（每层选哪个变体 + 版本三元组）→ verdicts.json / coverage.json / gaps.json → score.json
ledger.jsonl             run_id、git sha、config hash、benchmark hash、时长、费用（LLM 调用数）、谁跑的
scorecard.md             变体 × 指标，自动从 ledger 生成；差异归因列（和上一行差在哪一层）
```

规则：① 感知输出缓存（L1 固定 → 判定层变体之间比较不受重建噪声影响）；② 一次只换一层；③ 新变体先做**等价测试**（和基线在判定上应当一致的子集必须一致），再看它声称的改进；
④ LLM 变体记录调用数和费用；⑤ 每个 run 可用 `panoptes verdict run --config` 复现。

这和 `scripts/report_runner`（journal / profile / stage pins）与 `swap_generation.py`（变体表）的思路一致，复用它们的台账和 pin 机制，不另起炉灶。

## 2. 每层准备比较的方案

| 层 | 基线 | 候选变体 | 比什么 |
|---|---|---|---|
| L1 感知（先固定） | 照片流程 v2（SAM 3D + MVS 补洞 + 组装 v2） | 后期：DAAAM（视频）；WorldSGG 的持久性 | 对象召回、尺寸误差、σ 校准、coverage |
| L2 关系 | 盒面采样最近点 + 占用格 0.1 m | 网格级距离（trimesh）；占用格 0.05 m；places 由 coverage 生成 | 边值误差、U 覆盖率、运行时间 |
| L3 感知规约 | 无 | STPL 式监控 v1（持久性、尺寸一致、地面接触、coverage 阈值） | 误 FAIL 减少量、CANNOT_DETERMINE 的正确率 |
| L4 规范侧 | 逐句模板编译（8 月 / 10-07 试跑，当对照） | 条款图抽取（AEC3PO schema，表→查表函数）+ 对齐表（精确匹配 / 嵌入 / GinSign 式分类器）+ 检索（无 / BM25 / 嵌入 / 工位分类锚定） | 编译率、误拒率、对齐覆盖率 / 精确率、检索召回 |
| L5 检查合成 | 无（模板直出） | (B) 函数库映射（FuncMapper 式，对有类型 API）；(C) 代码合成 + 性质测试（TUM / CodeAct 式）；(E) 冗余翻译 + 差分执行（ARc 式）；(D) agent 工具提议 + 人签（RieMind 式，只收证据） | 可执行率、与手写参考规则的差分、每条审阅分钟、冗余不一致率 |
| L6 引擎 | clingo | SWI-Prolog（janus）；纯 Python 检查；pySHACL（RDF 导出后） | **判定必须 100 % 一致**（等价测试）；再比解释质量、速度、表达力 |
| 决策规则 | 护带 k=2 | k=1；简单接受；JCGM 106 概率式 | 混淆矩阵、FAIL 精确率 / 召回、inconclusive 率 |
| L7 解释 | 表 + 图 | 审阅屏 v1（条款 → 值 ± U → 阈值 → 判定 → 裁图） | 一分钟追溯率、"缺什么"一致率 |

每个变体一个目录、一个 `Protocol` 实现、一个 README（做了什么、来源、参数）。

## 3. 基准与金标（研究机构式）

- **基准 v0**：090、030（已有现场测量：罩壳 24.0、横杆 21.0 cm 等）+ 3 个合成原型（围栏工位、光幕工位、AGV 通道，参数化生成，真值免费）。
- **规范包 v0**：ISO 13857 + ISO 13855 的 20 条（含表 2 和 S = K·T + C）；v1 加用户的站点规则。
- **金标**：每 (工位, 规则, 对象) 人工五态判定 + 适用性 + 测量值；安全工程师双标 + 仲裁，α ≥ 0.8；每规则 ≥ 40 例、≥ 10 个 FAIL（合成场景补足）。
- **划分**：已见 / 未见工位 × 已见 / 未见规范包，分层报告（对象类别、规则类、工位原型）。
- **指标**：评测协议 §2 的分层指标；记分卡固定列顺序，便于横向比。

## 5. 角色、资源、风险

- 人：1 名工程师做 A / B / D；1 名做 C（LLM 侧）；安全工程师每周 2–4 小时做金标和签字（这是瓶颈，先约）。
- 资源：CPU 为主；LLM 调用用你们的 key（C 阶段每方案 20 条 × k 份冗余，百量级调用）；Modal 只在重算感知时用。
- 风险：① 金标没人标 → 先用合成工位；② ISO 正文拿不到 → 表格用厂商复述并标 unverified，拿到正文后只改查表函数；③ LLM 方案不稳定 → 冗余 + 差分兜底，不稳定本身就是记分卡上的一列。
