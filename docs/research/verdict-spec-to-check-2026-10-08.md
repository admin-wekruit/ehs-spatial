# 从自然语言规范到可执行检查：现有思路的批评与替代（2026-10-08）

背景：用户对"一句一句把规范整理进固定 RASE 模板 + 封闭词表 + 不能表达就拒绝"的思路不满意。本文是针对这一点的调研结论（全文和每条链接在附录 E
`verdict-spec-to-check-2026-10-08-survey-E.md`）。

**一句话结论：你的不满是对的。** 后半段（场景图 + 算出来的米制关系 + 确定性绑定 + 显式"不知道"状态）是领域正在收敛的做法；
前半段（逐句整理进固定模板、词表缺口就拒绝、没有文档上下文、没有检索、整理结果不验证）是领域已经走过去的做法。

## 1. 现有思路错在哪（有证据）

| 弱点 | 证据 |
|---|---|
| **词表缺口 → 拒绝，是错的策略** | NL → 逻辑的失败点是"落地"（grounding）不是"翻译"：VLTL-Bench（2025-12）提升式翻译 78–99 %，落地后端到端只有 26–72 %。对着签名做对齐的系统能救回大部分：GinSign 落地逻辑等价 95.5 %；GuardEn 的"检测置信度 < 0.8 就换同义词重落地"值 +16.5 F1；Zhang & El-Gohary 的 IFC-法规概念对齐约 80 %。我们把签名当门，直接丢掉条文 |
| **一句话一个单位，没有上下文** | 唯一的 RASE 式标注语料 CODE-ACCORD 只能收"自足"的句子，把需要上下文的全删了；RASE 作者自己是在嵌套章节和**表格单元格**上标；AEC3PO 本体有 Definition / Table 模块。ISO 13857 表 2、ISO 13855 的速度 / 公式条款、IEC 60204-1 的交叉引用定义都不可能逐句整理 |
| **固定模板 = 把 Solibri 的天花板重做一遍** | "一条边 + 算子 + 阈值"只覆盖 Solihin–Eastman 规则分类的 1–2 类；3–4 类要代码，所以 Solibri 开 Java API、TUM / FuncMapper 让 LLM 写或组合函数。CodeAct（ICML 2024）：代码动作比 JSON 动作成功率高最多 20 % |
| **单次整理不验证** | 整理就是自动形式化，没有冗余、没有等价检查、没有测试。ARc（AWS）要靠 k 份冗余翻译 + SMT 等价才到 > 99 % 可靠；"Know Your Limits"（2026-06）记录了"scope laundering"（不跑求解器就报答案）、漏隐含约束；P4IR 显示 Claude Opus 4.5 / GPT-5.2 零样本也会出结构错的规则骨架 |
| **没有检索** | 不必预先编译全部：DriveReg 按场景检索条款 100 %（20 场景，562 条规则），Lawful-AD 法规-场景匹配 +29 %。只有适用的条款才需要编译和审 |
| **规模和审阅成本没度量** | 这种设计没有任何每条成本数据；有数据的是"抽取 + 置信度分流 + 字面化审阅"的设计：Han et al. 2026 专家工时 1,620 h → 168 h（−90 %），I-SNACC 每个案例 13 min |

该留的强项：确定性绑定和判定（clingo）、五个状态（NEEDS_INPUT / NEEDS_MEASUREMENT / CANNOT_DETERMINE…；四值合规推理 MONIR 是当前理论）、护带、证据链、
场景图 + 算出来的米制关系——GuardEn 的消融说关系落地是最大的单项贡献（去掉 −30.1 %）。

## 2. 替代路线对比

| 路线 | 每条人工量 | 扩到几百页 | 表格 / 定义 / 例外 | 可审计 | 报告的准确率 | 成熟度 | 对米制 3D 规则 |
|---|---|---|---|---|---|---|---|
| 封闭词表 RASE JSON → ASP（现状） | 高（LLM 草稿 + 人整理，缺口即拒） | 差（无检索、无上下文） | 弱（句子单位） | 高（确定性） | 无 | 原型 | 后端好，前端差 |
| 函数库映射（LLM-FuncMapper 66 个原子函数、Solibri 模板、TUM） | 库建好后低–中；建库是成本 | 中（长尾函数） | 中（函数可包表格） | 函数经审则高 | top-5 检索 81.55 %；"~100 % 可表达"（自定义口径） | Solibri 商用；LLM 变体研究 | 好：边变成函数 |
| 逐条程序合成 + 测试 | 草稿低，要审 | 配检索则好 | 好（代码能读表 / 定义） | 中（代码审查） | 12 条规则跑通率 13–77 %（按模型）；PropTest +6–8 | 研究 | API 小而有类型则好 |
| Agent 在场景图上用工具（RieMind、MIT Cypher、SGR-BIM、CompAgent） | 极低 | 好 | 中 | 中（有 trace，判定非确定） | VSI 静态 85–89 %；679 条消防查询 84.3 %；F1 76–80 | 研究 | 适合收集证据，不适合出判定 |
| 语义解析到逻辑（I-SNACC、ACCORD） | 中–高（模式规则、标注） | 差–中 | ACCORD 建模了表 / 定义；句级解析器没有 | 高 | 一章 P 95.2 / R 100 | ACCORD 欧盟试点 | 中（为 BIM 建） |
| 检索 + 对齐（一级，不是整系统） | 极低 | 规模化必需 | 要结构化 KG | 中 | 匹配 100 % / +29.1 %；多跳 F1 87.3 | 研究，易做 | 必需 |
| 自动形式化 + 验证（ARc、nl2spec、P4IR） | 草稿低，交互修（平均 1.4 轮） | 好 | 签名要含表 | 极高（工件、测试） | > 99 % 可靠；交互 86.1 % | ARc 商用 | 好：ASP 是合适的目标 |
| VLM 直判 | 零 | — | 无 | 低 | F1 61–73；家居 34.7 | 已部署（MonitorVLM-v2） | 米制阈值差 |
| GuardEn（编译 + 场景图落地） | 低（验证过的分解） | 中 | 表格弱 | 高（命题树） | F1 78.7 均 / 86.4 建筑 | 研究，强 | 最近的亲戚；缺米制表格和护带 |

## 3. 推荐架构：用"抽取"代替"整理"，判定仍确定、可审计

| 级 | 做什么 | 抄谁 |
|---|---|---|
| 1 文档 → 结构化条款图 | 节点：标准版本、条款、定义、表、图、注、交叉引用。**表变成带类型的查表函数**（`iso13857_table2(hazard_h, structure_h) → 水平距离`），定义变成别名集，例外变成 defeater 边。LLM + 版面解析抽取，**每份文档审一次**，不是每句 | BifrostRAG 文档导航图、AEC3PO 的 Definition / Table 模块、EDC 规范化、Akoma Ntoso 版本 id、LegalRuleML 可废止 |
| 2 概念对齐（学习 + 缓存） | 条款词 → 场景类别 / 区域 / 属性的对齐表，带置信度；工程师审**表**（几十行），不审每条条文。"vocabulary_gap"变成"对齐低于阈值 → 待审行"，不是拒绝 | GinSign 结构化分类、GuardEn 同义词重落地、Zhang & El-Gohary transformer 对齐 |
| 3 按场景检索适用条款 | 两级检索，锚在工位分类（机器人、固定防护、光幕、开口、操作区）；只有检索到的条款进下一级；检索集记录备审 | DriveReg、Lawful-AD |
| 4 对小型有类型的场景 API 合成检查 | API = 现有关系库（3D 距离、水平距离、离地缝、z 重叠、越过三元组、视线、占用）+ 查表函数 + `declare_input(…)`。LLM 输出一段短检查（Python 或 ASP）+ 子翻译（条文片段 ↔ 用到的 API 调用） | CodeAct / TUM、FuncMapper 组合、nl2spec 子翻译、以后 P4IR 式骨架 IR 做微调 |
| 5 人看之前的自动验证 | k 份冗余翻译在生成的测试场景上**差分执行**（ARc 的思路，用场景代替 SMT）；LLM 写性质测试（PropTest）；签名验证器拒绝未知谓词（LogiSafetyGen）；蜕变测试（缩放场景判定不变、跨阈值必翻）。不一致 → 带 diff 进审阅队列 | ARc、PropTest、LogiSafetyGen |
| 6 字面化审阅 | 每条条款一屏：条文高亮片段、子翻译、检查代码、测试场景及判定、用到的对齐行；置信度分流，工程师只审不确定的 ~20 % | nl2spec 表、AWS 精修屏、Catala 字面化、Han et al. 分流 |
| 7 确定性执行 + 证据 | 审过的检查编译成 ASP（或作为纯函数产事实进 clingo），四值 + 护带，每条判定的证据 = 条款 id、表行、测量值 ± U、对齐行 | 现有引擎 |

**先做什么（两周量级）**：第 1 级只做 ISO 13857 + 13855（表和定义变函数）；有类型的场景 API 就是现有关系库；第 4–5 级跑 20 条检索到的条款；审阅屏先做静态 HTML。
在同一批 20 条上和现在的编译器对比。

**度量**：编译率（可执行且未拒绝，目标 > 80 %）、对齐覆盖率、每条审阅时间（秒表；Han 式每文档工时）、与工程师在留出场景上的判定一致率（κ + 含 CANNOT_DETERMINE 的混淆矩阵）、
误拒率、适用条款检索召回（对工程师清单）、冗余翻译不一致率（歧义代理，ARc 的 TRANSLATION_AMBIGUOUS）。

## 4. 丢什么、留什么

- **丢**：逐句固定 JSON 模板作为编译目标；词表缺口即拒绝；"一条边 + 算子 + 阈值"作为唯一的要求形状；预先编译全部；不验证的单次整理。
  → `research/verdict-layer-trial-2026-10-07/{compiled_v1_draft.json, compile_prompt.md}` 标为已被取代，`rase_schema.py` 的验证器思路保留为签名验证器。
- **留**：薄场景图（有向盒、高度、σ）；关系库（升级成有类型的 API）；clingo 绑定和确定性；护带；五个判定状态；证据链；类别 / 区域 / 边的封闭集合——作为**对齐的签名**，不是**拒绝的门**。
