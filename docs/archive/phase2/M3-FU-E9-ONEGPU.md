# M3 追加实验 E9：一块 A100 跑完整核心，和两块比（ME340，2026-09-28）

回答两个问题：一块 GPU 能做到多快？第二块 GPU 带来什么？

探针：`modal_apps/m3_fu_e9_onegpu.py`，单文件，Modal 临时 app，retries 0。复用了 E1/E7 的 `fuse`、`edge_filter`、`align_sim3`（`modal_apps/m3_exp_geometry.py`），E5 的事件比对（`modal_apps/m3_e5/vllm_events.py`），E2 的 40 词表和 GPU 预处理，以及 `detect_shot_cuts.py` 的切点规则（没改）。

标注：[M] 实测，[E] 估计。结果目录在 `research-notes/phase2/runs/` 下：
- `m3-fu-e9-onegpu-003`：正式轮。
- `m3-fu-e9-onegpu-001`：上一版，SAM 3 要等切点算完才开始；这一轮有 MPS 对照。

每个目录里有 `*gpu*.json`（每次调用的分段时间和各层结果）、`evaluation.json`（质量），以及最后一次调用的网格和点云。

## 结论

"核心层就绪"指相机轨迹、房间网格、点云、人和轨迹、带名字的物体框、事件全部出来。计时从 MP4 字节进入容器开始，全部是热启动 [M]，数据来自 run 003：

| 配置 | 核心层就绪 | 说明 |
|---|---|---|
| 1×A100，串行 | 49.2 s（首次调用 53.4 s） | 同一套代码，各段一个接一个跑 |
| **1×A100，重叠** | **37.4 / 37.6 s** | 解码时就把关键帧喂给 SAM 3；DA3 和 SAM 3 在各自的 CUDA stream 上并发；事件在 vLLM 进程里同时跑 |
| 2×A100，按计划静态分工 | 29.3 s（首次 31.8 s） | GPU A：DA3、TSDF、抬升；GPU B：SAM 3、事件 |
| **2×A100，动态分工** | **20.4 / 20.9 s** | SAM 3 的活放进一个队列，GPU A 在切点出来之前、DA3 做完之后都去领活 |

- **一块 GPU 可以优化**：从串行的 49 s 降到 37.5 s（快 24%），质量不变。一块 A100 的下限大约是 GPU 纯计算量之和，约 32 s（SAM 3 24.0 s + DA3 7.6 s）[M]，再加事件占用的一部分，实际大约 33–35 s [E]。现在的 37.5 s 离这个下限不远。
- **第二块 GPU**：用动态分工，从 37.5 s 降到 20.4 s（快 46%）。按计划的静态分工只到 29.3 s，因为 SAM 3 单独就要 24 s，全压在 GPU B 上，是最长的一段。所以要用第二块卡，SAM 3 必须能在两块卡上分。
- **瓶颈是 SAM 3，不是 DA3、融合或事件**：{人, 地面} 在 5 fps 上跑 150 帧，40 词在 50 帧上跑，单卡合计 24 s。融合、抬升、人加起来不到 0.5 s。
- **质量在所有模式下完全一样**（同一轮内逐项相同）：走动镜头位姿对 DROID 的 ATE 为 0.041 m；我们用 SAM 3 地面平面加 1.6 m 相机高得到的尺度，是参考尺度的 0.990 倍；164 个确认物体，参考召回率 0.53（0.5 m 内）；事件 4/4 对上，人物、PPE、安全备注三项完全相同。

## 各段单独耗时（run 003 串行 2，1×A100 PCIe，热）[M]

| 段 | 耗时 | 说明 |
|---|---|---|
| 解码 899 帧 720p、选关键帧、上传 GPU | 1.7 s | OpenCV 解码；灰度和清晰度在线程里算；每 6 帧取最清晰的一帧，共 150 个关键帧，每 8 帧上传一次 |
| 切点 | 解码结束后再 5.3 s（累计 7.0 s） | `detect_shot_cuts` 规则，64 帧一块，放在 12 个进程里算，结果与顺序算完全一致（自检覆盖）。切出 [0,13] [14,225] [226,898]，和缓存一致 |
| DA3-GIANT any-view | 1.2 s + 6.4 s | 两个镜头分别 34 和 113 个视角，504×280；在 GPU 上缩放和归一化后直接前向，结果不回 CPU |
| SAM 3 | 24.0 s | {人, 地面}：19 组，每组 8 帧；40 词：50 帧（每 3 个关键帧取 1 个），复用视觉特征；bf16；只对保留的查询上采样掩码 |
| 地面平面、TSDF、点云、人 | 0.3 s | Open3D CUDA，3 cm；网格共 189 万三角形，点云 105 万点 |
| 抬升、合并、命名 | 0.04 s | E7 的体素重叠规则，名字取词表投票 |
| 事件 | 10.1 s | Qwen3-VL-8B，vLLM 0.11 eager，两个窗口同时发；输入 7678 和 11431 个 token，输出 116 和 286 个 |

- 事件比 E5 的"热 4.4 s"慢，是因为这里每次都是新的图像请求，经过 OpenAI 接口的服务端。E5 的 4.4 s 是同一批提示重复发送的第二次，E5 第一次也要 10.6–11.7 s。
- 事件不在关键路径上：重叠模式下 12–15 s 就做完了。

## 一块卡上试过的办法 [M]

| 办法 | 效果 |
|---|---|
| 切点改用进程并行，不用线程 | 解码加切点从 22–38 s 降到 7 s（smoke 对 001）。线程不行，因为切点代码在 OpenCV 调用之间有 Python 循环，一直持有 GIL，还和解码抢 CPU |
| 重叠：DA3 和 SAM 3 各用一个 CUDA stream，事件同时跑 | 48.2 s 降到 40.3 s（001） |
| 解码时就喂 SAM 3，不等切点 | 40.3 s 降到 37.5 s（003）。1 块卡时切点已经不在关键路径上 |
| MPS（让 vLLM 进程和主进程的核函数同时跑） | 39.4 s 对 40.3 s，差别在噪声内；2 块卡上没有收益。MPS 能让事件和 SAM 3 同时跑，但关键路径是主进程里 SAM 3 和 DA3 的计算，本来就把卡占满了 |
| 对 SAM 3 用 torch.compile | **失败**，没测到数：Inductor 生成 Triton 代码时报 `KeyError: triton.language.bfloat16`（镜像里 torch 2.14 和它自带的 Triton 不配）。Modal 反复重启崩掉的容器，直到我停掉 app |

一块卡上还能挖的 [E]：
- SAM 3 编译、TensorRT 或换更新的 Triton：常见收益 1.1–1.3 倍，也就是 3–5 s。
- 词表改成每 4 个关键帧跑一次：省 3–4 s，但会影响召回，要重测。

## 第二块卡的细节（run 003 动态分工 3）[M]

- **GPU 0**：
  - 0–8.6 s：做 SAM 3，10 组 {人, 地面}、9 帧词表。
  - 8.6–15.7 s：DA3，要等切点出来。
  - 到 16.2 s：TSDF 和人。
  - 16.2–20.3 s：又做了 14 帧词表。
- **GPU 1**：
  - 0–20.3 s：做 SAM 3，9 组 {人, 地面}、27 帧词表。
  - 4.7–14.6 s：同时跑事件。
- 20.37 s 抬升做完，核心层就绪。

剩下的关键路径是 CPU 上的切点：DA3 要到 8.6 s 才能开始。如果切点能做到 2 s 左右（更多 CPU，或只在镜头边界附近细算），两块卡能到 16–17 s [E]。另外，两个 SAM 3 线程抢 GIL，解码从 1.7 s 拖到 4.5 s。

## 冷启动、传输、显存 [M]

- **冷启动**：容器进入后到可用要 91–116 s。其中：
  - import 22–30 s。
  - DA3 权重从 Volume 读 12 s，SAM 3 读 3–4 s。
  - vLLM 健康检查通过在 83–107 s，是冷启动里最长的一段。它先起，其余的加载和它重叠。
  - 预热 8 s。
- **从提交到可用**：有空闲容量时 107–122 s（001）；排队等 A100 时 231–273 s（003）。演示一定要 `min_containers=1`。
- **传输**：
  - 6.5 MB 的 MP4 进去、只拿回 JSON：客户端墙钟比容器内多 1.2–2.4 s。
  - 同时拿回约 95 MB 的网格和点云：多 5–12 s（生产环境应由容器直接写云端）。
- **显存峰值**：整卡用量，含 vLLM 固定占用的 0.35，约 28 GB。

  | 配置 | 峰值 |
  |---|---|
  | 1 卡，串行 | 65.6 GB |
  | 1 卡，重叠 | 77.5 GB，离 80 GB 只差 2.5 GB |
  | 2 卡，动态分工 | GPU 0 为 35.5 GB，GPU 1 为 48.0 GB |

  1 卡重叠模式下，视频更长、单个镜头关键帧更多时，DA3 的显存会涨，可能爆显存。这时要按镜头分批，或者把 vLLM 的占比压到 0.30。

## 质量细节 [M]（evaluation.json）

- **位姿和尺度**：走动镜头按 Sim3 对齐到 DROID。
  - 001：ATE 0.043 m，和 E1 GIANT 504 一致；尺度是参考的 0.998 倍。
  - 003：ATE 0.041 m；尺度 0.990 倍。
  - 地面平面拟合的内点，003 走动镜头有 12.6 万个。两边都假定相机高 1.6 m。
- **物体**：
  - 003：走动镜头 164 个确认物体（至少 2 帧）；参考物体图里 96 个实体，0.5 m 内召回 0.53（0.3 m 内 0.41）；我们的物体 0.5 m 内有参考的占 0.70。
  - E1 用 SAM 2 全图掩码是 0.64，40 词表少召回一些。
  - 词表的词出现在参考名字里的只占 0.08。参考名字是自由文本，比如 "electrical conduit"，这个数只能说明两者不是同一套名字。
- **人**：每个镜头各一条 3 次以上检测的轨迹，是讲解人。走动镜头有 115 次检测。轨迹只做了最近邻连接，E3 有完整版。
- **事件**：和 `me340-events-197` 比，4/4 对上，时间 IoU 为 1.0，人物、PPE、安全备注完全相同；标题用词的 Jaccard 为 0.36 和 0.86。

## 注意

- DA3-GIANT 是 CC BY-NC，只能用于演示（见计划第 6 节）。
- 事件用 vLLM eager 模式：冷启动快（vLLM 83–107 s 可用），解码没有 CUDA graph。编译模式加载要 144 s（E5）。
- 关键帧在全局每 6 帧取一个，不按镜头起点对齐。落在不满 30 帧镜头里的 3 个关键帧，SAM 3 白算了。
- 只测了 ME340 一段，只有一个讲解人。人多、镜头多、视频长的片子，SAM 3 的份额还会更大。
- 快速版要求 2–3 分钟出报告。核心层单卡 37.5 s、双卡 20.4 s 之后，还有 SAM 3D、泼溅（gsplat 5k 步 159–182 s）、云端写入和查看器。单卡上泼溅只能排在核心层后面，约 200–220 s [E]；双卡时泼溅可以在 DA3 出位姿后就上另一块卡 [E]。这才是第二块卡对 2–3 分钟目标最大的价值，E9 没有测。
