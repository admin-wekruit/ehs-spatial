## 0. 本轮做了什么

- **完整 oneshot**：在 2×A100-80GB 临时容器跑通，四张原图到可打开报告共 915.9 s。语义阶段绑定在本次运行上，不是 `not_bound`。
  - 最慢的是 GPU 容器里的 CPU 后处理，483.5 s，其中物理下沿提取 457.4 s。
  - GPU 显存峰值：MapAnything 8.38 GiB，语义编码器 2.6 / 3.6 GiB；SAM 3 和 RecGen 未记录。
  - 费用估计（本轮全部 7 次 GPU 调用）：函数窗口 $1.722，调用窗口 $2.271，其中失败 $0.223（第一次外壳实验，是本轮新代码的问题，已修）。已写入总账。
- **一个场景，一个对象一个模型**（回应 3D 场景截图）：
  - 页面不再按所选照片替换机器人模型；场景固定显示照片 4 的模型。
  - 39 个原始单照片点云碎片整理为 11 个对象，每个对象一个干净代理：贴地或平面照片纹理四边形、盒子；工作区外的对象只留照片观察。规则在 `scripts/workcell_extra_models.py`，objects 阶段末尾直接调用。
  - 对象 52 → 24，观察 97 → 91。语义用 `semantic-match-protocol-2026-10-03.json` 重跑；以后的 oneshot 要用这份协议，因为旧协议按 52 个旧编号写。
- **目录复核**：
  - fence-0 照片 2 的 14 像素观察在立柱边缘，按几何阶段的面板最小支持规则移除；
  - 复核后语义为 `not_bound`，重跑后重新绑定；
  - 新运行由 objects 阶段直接拒收此类观察。
- **可见尺寸按本版本帧和地面重测**：沿用 objects 阶段的支持规则，不用外轮廓多边形。
  - SAM 掩码解码改为与 OpenCV 版本无关的确定性最近邻。
  - 本运行页面显示的可见高度只变了 post-box-1 −0.18 cm。
- **光幕面身份（P1-1）**：
  - 两根光幕在四张照片里混用宽板 B 与窄边板 L 两块不同的面，拟合下沿是两块板下沿的混合，**单一矩形面模型不成立**。
  - 照片 1 另有相机 1 约 0.5–0.8° 偏航的可能，是假设，未调相机。
- **左右围栏下沿（P1-2）**：
  - 两侧是同一类白色底部框管，但左侧点是“下包络假设”，不是框管下沿，在照片 2 高 48 px；
  - 原 5.79 cm 左右差不是同类比较。报告现在标注假设，拒绝含假设点的相减。
- **两轮独立对抗审查**的发现都已修复并加了回归检查（ONESHOT 第 7 节；第二轮结果见下）。

## 2. 下一会话先做

1. **光幕两板模型**（P1-1 后续）：
   - 先给每条边线和端边标定它属于宽板 B 还是窄边板 L 的哪条物理边，并在四张照片之间固定；
   - 再选两板模型（B + 斜置 L），或只用 B 自己的边去拟合 B；
   - 写明离地测量用的是哪块板的下沿。
   - 做完之后，再用无歧义的边（立柱侧边）核对相机 1 的偏航假设。
   - 不加迭代，不调相机，除非核对证明需要。
2. **左下沿在几何阶段测出来**（P1-2 后续）：
   - 照片 2 已检到左框管下沿（h≈0.266），但按线段长度比例配不成梁；改为按 native 面高上限配对，或接受最低的“下暗上亮”长边；
   - 再从另一个不被遮挡的视角三角化。
   - 在此之前，保持“不比较”。
3. **速度**：后处理（物理下沿提取 457 s）移出 2×A100 容器，或并行化，GPU 费用约 70% 在这里。
4. **公开重放带支持输入**：`workcell_replay_inputs.py` 不复制 `cart-input.npz` / `guard-input.npz`，所以公开重放的可见尺寸会标为 objects 阶段值。要么发布这两个掩码，要么接受这个标注。
5. **悬空的灯与标识**：信号灯和顶部标识挂在龙门架上，龙门架和天花板没有建模，所以看起来悬空。下一步可以从围栏端柱的检测线拟合龙门架；信号灯这类小的 3D 物体可以用 RecGen 生成，目前是盒子。
6. **其余**：三尺寸标尺与局部地面、护板实物角度、参考图 prelist（GPU）、开放词汇检索、跨图语义独立标注。
