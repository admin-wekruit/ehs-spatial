# 端到端证明（2026-10-07）：clone + .env + endpoint 这条路通了

**要证明的**：客户的工程师只做 `git clone` → 填 `.env`（凭证 + jumpbox 端点）→ GPU 机 `make up` → `panoptes run`；流程里的模型推理走 HTTP 服务（契约 `docs/BACKENDS-v1.md`），算法不变。

**怎么证的**（`research/module-swap-2026-10-07/e2e_sam3d_http.py`）：
- 服务端：`serving/sam3d_service.py`（真模型 SAM 3D Objects `facebook/sam-3d-objects@2e73555`，`PANOPTES_WEIGHTS_MODE=hf-cache`，API key）起在 Modal 的 A100-80GB 容器里（镜像 = 我们的 SAM 3D 镜像 + 这个仓库的 `serving/`、`ehs_spatial/` 和 ehs-spatial 的 `scripts/onprem/`），`modal.forward(8805)` 隧道当作客户的 jumpbox 端点。临时运行，没有部署。
- 客户端：本机（无 GPU），`SAM3D_BACKEND=http SAM3D_HTTP_URLS=<隧道>`，流程的 provider `ehs_spatial/providers/sam3d.py` 用 090 补洞几何的真实物体输入（`completion_ab.sam3d_inputs`）调用 `POST /v1/sam3d`。

顶点数差 2（10⁻⁵ 量级）= GPU 非确定性，在 prompt 第 5 节的容忍内；外接范围逐位相同。第二次同输入调用由服务端幂等缓存直接返回。

**过程中踩的坑（都已改）**：服务模块按同目录导入（`import v1_common`）→ 要从 `serving/` 目录启动（compose 栈就是这样）；`PANOPTES_WEIGHTS_MODE=hf-cache` 用于权重已在 HF 缓存里的主机；我这边两次旧的本地进程没退干净、往同一个日志写，导致以为容器导入了旧模块——和产品无关。

**没在这里证的**：`geometry-mvs` 服务的真 GPU 跑（RoMa + DA3-BASE + MoGe-3；中间结果已随仓库 `data/` 给出，默认跳过）；Docker 镜像在客户机上的构建；Mongo / S3 真实后端（契约测试用 mongomock / moto 过，真实后端的参数在 `docs/STORAGE.md`）。这三项在客户机上按 `HANDOFF.md` 的验收 A1–A6 走。
